**版本：** 1.0（基于当前实现整理）
**日期：** 2026-06-14
**配套文档：** 《设计说明书》`docs/设计说明书.md`

本文件汇总框架的**需求**（做什么、必须满足的约束），由分散在 `docs/superpowers/specs/` 的逐特性设计文档与当前代码实现整理而成，作为单一权威需求参考。设计与实现细节见配套《设计说明书》。

---

## 1. 引言

### 1.1 目的
定义一个 C++ 通信中间件库的功能与非功能需求。该库将**数据传输**与**数据编解码**解耦：负责跨多种协议（TCP / UDP / 串口 / DDS）的原始字节流收发，不关心数据的类型、格式与内容；编解码由用户实现的 `ICodec` 在收发边界由框架自动调用。

### 1.2 范围
- **是：** 一个可静态/动态链接的传输库，提供统一的收发抽象、可插拔编解码、流式分帧、运行期寻址、单连接多帧格式（topic 路由）、统一工厂创建。
- **不是：** 消息代理 / 路由守护进程；不解析、不解释、不转换消息内容（`ICodec` 之外的部分）。

### 1.3 术语
| 术语 | 含义 |
|---|---|
| 传输（transport） | 一条收发通道的统一抽象（`ITransport`） |
| codec | 用户实现的编解码器（`ICodec`），框架在发送前 `Encode`、接收后 `Decode` |
| 分帧（framing） | 把字节流切分为完整帧（仅流式传输接收侧） |
| topic | DDS 原生主题；或流式/报文传输上用于区分帧格式、选 codec 的逻辑通道名 |
| Endpoint | 中立的寻址目的地值类型（默认 / 网络 ip:port / topic） |
| provider | DDS 底层库的抽象适配（`IDdsProvider`），如 Fast DDS |

### 1.4 参考
逐特性设计文档（已并入本 SRS 与《设计说明书》）：主 spec `2026-06-09`、Foundation/TCP as-built `2026-06-10`、UDP/串口/DDS/Endpoint/topic 路由/Factory 各 spec。

## 2. 总体描述

- **平台：** Linux（桌面/服务器）。
- **使用场景：** 本机进程间通信 + 跨网络通信（混合）。
- **集成：** 静态库 `.a` 或动态库 `.so`，应用层直接链接。
- **用户：** C++ 应用开发者，持有 `shared_ptr<ITransport / ITcpServer / IDdsTransport>` 进行收发。
- **核心假设：** 用户负责消息的语义编解码（通过 `ICodec`）；框架只搬运字节并在边界回调 codec。

## 3. 功能需求

### FR-1 统一传输抽象
- **FR-1.1** 所有传输实现统一的 `ITransport` 接口：生命周期（`Open`/`Close`/`IsOpen`）、发送、接收、断连通知、codec 挂载。
- **FR-1.2** 发送：`Send(data)` 发往实例创建时绑定的默认目的地，`data` 为 `std::vector<uint8_t>`（自带长度，无 `len` 参数）。返回的 `Status` 表示**入队/写出成功**，不代表对端已收。
- **FR-1.3** 接收提供三种模式，同一实例上**互斥**，由 `Open()` 后首次接收调用确定、之后不可切换：
  - 同步 `Receive(timeout_ms)`（阻塞，`0`=永久）；
  - 回调 `OnReceive(cb)`（cb 在内部 I/O 线程执行，必须非阻塞）；
  - future `AsyncReceive()`（每次消费一条，多个未决 future 按到达顺序 FIFO 兑现）。
- **FR-1.4** 断连通知 `OnDisconnect(cb)`（TCP 客户端、串口适用）。
- **FR-1.5** 连接级错误也以 `Result<Message>{ok=false}` 经接收队列/回调投递。

### FR-2 寻址发送（Endpoint）
- **FR-2.1** 提供中立寻址值类型 `Endpoint`（`Default` / `Net(ip,port)` / `Topic(name)`），零第三方依赖，镜像 `Message` 的 `source`/`topic`。
- **FR-2.2** `Send(data, Endpoint)` 为基类非纯虚、默认实现：`kDefault` 退化为 `Send(data)`，其余 kind 默认 `Fail("io: addressed send not supported")`；UDP 覆写 `kNet`，DDS 覆写 `kTopic`。
- **FR-2.3** 持有基类句柄 `shared_ptr<ITransport>` 即可寻址发送，无需向下转型。
- **FR-2.4** 寻址错误语义：UDP 传入非法地址 → `config: invalid address`、传入 `Topic` → `config: udp expects net endpoint`；DDS 传入 `Net` → `config: dds expects topic endpoint`。

### FR-3 编解码扩展点（ICodec）
- **FR-3.1** `ICodec` 提供 `Encode`/`Decode`，均返回 `Result<std::vector<uint8_t>>`（可报错）。
- **FR-3.2** 框架在发送前自动 `Encode`、接收后自动 `Decode`；用户**不**直接调用。
- **FR-3.3** 未设置 codec 时字节原样透传（恒等）。
- **FR-3.4** `Message.payload` 在收发两侧恒为「应用原始字节」（`Decode` 后 / `Encode` 前）。

### FR-4 流式分帧（IFramer）
- **FR-4.1** 提供 `IFramer` 接口与内置 `LengthFieldFramer`（适配「固定 header + header 内长度字段」协议，可配 header 大小、长度偏移/宽度（2/4/8）、字节序、长度是否含 header、帧长上限）。
- **FR-4.2** 分帧仅作用于流式传输（TCP/串口）**接收侧**；UDP/DDS 报文天然保边界，不分帧。
- **FR-4.3** 发送侧不分帧、不加前缀（非 topic 路由时）：codec 输出原样写出。
- **FR-4.4** 未配置 framer 时接收为透传模式：每次底层读到的字节即一条 `Message`。
- **FR-4.5** 帧头非法 / 帧长越界 → `frame:` 错误并断开。

### FR-5 topic 路由（单连接多帧格式）
- **FR-5.1** 一条 TCP/UDP/串口连接上承载多种帧格式：发送按 `Message.topic` 选 codec 编码并打 in-band 信封；接收按 topic 解信封 + 选 codec 解码。
- **FR-5.2** 框架维护 `topic→codec` 注册表：`SetCodec(topic, codec)` 注册，未注册 topic 回退默认 codec（`SetCodec(codec)`），默认也无则透传。
- **FR-5.3** 新增 `Send(const Message&, Endpoint=Default())`，使发送侧与接收侧 `Message` 对称（`Send(Receive())` echo 可往返）。
- **FR-5.4** opt-in：TCP/UDP/串口经各自 config 的 `enable_topic_routing`（默认**关**）开启。关闭时与旧帧格式**逐字节一致**；此时 `Send(Message{topic 非空})` 返回 `config: topic routing not enabled`。
- **FR-5.5** DDS 例外：topic 是 DDS 原生维度，注册表始终在线、**无开关、无信封、线格不变**。
- **FR-5.6** topic 上限 65535 字节（`uint16` 长度字段），超限 → `frame: topic too long`。

### FR-6 TCP 传输
- **FR-6.1** 客户端：连接 `host:port`，支持连接超时与 `auto_reconnect`（指数退避自动重连，重连时仍触发 `OnDisconnect`）。
- **FR-6.2** 服务端（`ITcpServer`）：监听 `bind_addr:port`，`max_clients` 限制；`OnNewConnection` 为每个被接受连接交付独立 `ITransport`；`GetClients` 快照；`DisconnectClient(client_id)` 按 "ip:port" 主动断开。
- **FR-6.3** 服务端继承的 `Send(data)` = 向所有已连接客户端**广播**；服务端自身的 `Receive`/`OnReceive` 不适用（应在每客户端 transport 上收发）。
- **FR-6.4** 客户端与服务端被接受连接共用同一收发实现（`ITransport` 行为一致）。

### FR-7 UDP 传输
- **FR-7.1** 单类支持三模式：单播 / 组播 / 广播。
- **FR-7.2** `Send(data)`：单播/广播发往 `remote_addr:remote_port`，组播发往 `multicast_group:remote_port`。
- **FR-7.3** 运行期寻址：`Send(data, Endpoint::Net(ip,port))` 发往指定地址，忽略默认 remote。
- **FR-7.4** 接收 `Message.source` 含发送方 "ip:port"。
- **FR-7.5** 组播可配 TTL；本地绑定 `local_addr:local_port`（`0`=OS 分配）。

### FR-8 串口传输
- **FR-8.1** 配置设备路径、波特率、数据位、停止位（1/2）、校验位（N/E/O）。
- **FR-8.2** 字节流语义，接收侧分帧规则同 TCP（可选 framer，未配置则透传）。

### FR-9 DDS 传输
- **FR-9.1** 一个 `IDdsTransport` 实例 = 一个 `DomainParticipant`（绑定 `domain_id`），实例内部以懒加载维护多个 topic（按 topic 发布/订阅）。
- **FR-9.2** pub-sub：`Send(data, Endpoint::Topic(name))` 按 topic 发布（`Send(data)` → `topics[0]` 默认 topic）；`Subscribe`/`Unsubscribe` 动态订阅，收到消息 `Message.topic` 标识来源。
- **FR-9.3** req-resp（建于 pub-sub 之上，provider 无关）：
  - 客户端 `SendRequest(data, topic, on_reply, timeout_ms)`：框架生成 `request_id`、订阅 `<topic>_Reply`、自动配对响应或超时（`on_reply` 收到 `Success(msg)` 一次，或 `Fail("timeout:...")`）。
  - 响应端 `OnRequest(topic, handler)`：订阅 `<topic>_Request`，handler 收到请求 `Message` 与绑定的 `ReplyFn`，可同步或异步回包。
- **FR-9.4** QoS 简化结构 `DdsQos`（reliability：reliable/best_effort；durability：volatile/transient_local；history_depth），provider 负责映射到底层 DDS QoS。
- **FR-9.5** DDS 承载统一为不透明字节流：内置 `RawMessage`（`request_id`/`reply_topic`/`payload`）+ 自定义 `TopicDataType`，绕过 IDL/Fast DDS-Gen/Fast CDR，手写紧凑序列化（见《设计说明书》wire layout）。
- **FR-9.6** provider 抽象 `IDdsProvider` + `DdsProviderRegistry`：可接入其它 DDS 实现；关联/超时/id 配对在 `DdsImpl` 层完成，provider 只负责「按类型在指定 topic 上收发字节」。

### FR-10 统一工厂
- **FR-10.1** `TransportFactory` 是创建所有传输实例的唯一入口；类型化 `Create(config)` 返回各传输最具体接口（TCP 客户端/UDP/串口→`ITransport`，TCP 服务端→`ITcpServer`，DDS→`IDdsTransport`）。`Create` 不失败（配置校验延后到 `Open()`）。
- **FR-10.2** JSON 配置文件方式 `CreateFromFile(path)` 返回 `Result<vector<shared_ptr<ITransport>>>`；解析传输对象数组，每条一个实例。
- **FR-10.3** **严格校验**：未知 type / 未知字段 / 类型不符 / 枚举非法 / 必填缺失 → `config:` 错误（含条目序号与字段名），不静默忽略；任一条目失败 → 整体失败，不返回部分结果。
- **FR-10.4** 公共头文件不暴露 JSON 库类型（抽象层零第三方依赖）。

### FR-11 错误模型
- **FR-11.1** 框架**不抛异常**；所有可能失败的操作返回 `Result<T>` / `Status`。
- **FR-11.2** 错误字符串按前缀分类：`timeout:` / `conn:` / `codec:` / `frame:` / `io:` / `config:`。

## 4. 非功能需求

- **NFR-1 语言/标准：** C++17；CMake 构建；遵循 Google C++ 风格指南。
- **NFR-2 无异常：** 全框架不抛异常，统一 `Result<T>` 错误通道。
- **NFR-3 并发模型：** 每个收数据的传输实例内部一个 I/O 线程（`Open` 启、`Close` 停）；socket 读写与共享状态经 strand 串行化；异步 handler 以 `shared_from_this` 保活。`Send` 线程安全（入队由 I/O 线程写出）。
- **NFR-4 解耦与隔离：** 传输抽象层（`include/`）只含纯接口 + 数据结构，**零第三方依赖**；每个实现模块仅依赖自身底层库（asio / Fast DDS / termios），实现间互相隔离；第三方库被关在 `*Impl` / provider 内部。
- **NFR-5 可扩展/可替换：** 经 `I*` 接口可替换实现、可用 fake 测试上层；DDS 可经 `IDdsProvider` 接入新库。
- **NFR-6 自包含离线构建：** 第三方依赖（asio、nlohmann/json、googletest）已 vendored 进 `third_party/`，**零联网拉取**，离线即可完整构建+测试。
- **NFR-7 可选 DDS：** Fast DDS 2.13+ 为**唯一可选外部依赖**，CMake `find_package` 自动探测；未装时跳过 `FastDdsProvider` 及其真实互通测试（DDS 业务逻辑仍可用 `FakeDdsProvider` 测试），装后自动启用。
- **NFR-8 可测试性：** DDS 业务逻辑零 FastDDS 依赖（`FakeDdsProvider` 内存回环）；codec/framing 边界可用 mock 验证调用次数与顺序；回环集成测试覆盖各传输。
- **NFR-9 互通性：** DDS 经固定 wire layout（`RawMessage`）与外部 DDS 实现互通；topic 路由信封格式固定，两端 config 须一致。

## 5. 外部接口需求

- **5.1 库 API：** 公共头文件 `include/transport/*`（接口 + 数据结构 + 配置 + 工厂），不含第三方类型。
- **5.2 配置文件：** JSON（`transports` 数组），字段名 = config 结构体字段名，枚举用字符串，`framer`/`qos` 为子对象。
- **5.3 第三方库：** standalone Asio ≥1.28（TCP/UDP/串口）；Fast DDS 2.13+（可选）；nlohmann/json ≥3.11（JSON 配置）；GoogleTest ≥1.14（测试）；POSIX termios（串口）。

---

## 6. 约束与假设
- 仅 Linux；C++17；Google 风格。
- codec 须产出自带长度的帧（非 topic 路由的流式传输下，接收分帧依赖 codec 内嵌的长度字段）。
- topic 路由开启时 codec 只编解码 body，分帧由框架信封负责；两端 `enable_topic_routing` 必须一致。
- DDS 互通要求对端实现同名 `RawMessage` type 并遵循同一 wire layout。
