# ADR-0018：性能基准测试——双机双进程，方法学照 Fast DDS 3.6.1

**状态：** Accepted
**日期：** 2026-09-10
**关联：** 方法学参照 **Fast DDS 3.6.1** `test/performance/{latency,throughput}`；ADR-0007 **D3**（写侧 fire-and-forget、无背压——决定了吞吐口径必须两侧分别计数）；ADR-0014（框架无观测面——决定了丢失只能由测试自行计量）；ADR-0013 **D3**（`INTRAPROCESS_FULL` 的同进程交付——**双机形态使该问题不复存在**）；SRS **§3.6.2**（性能与容量需求——本 ADR 产出其证据，但不充当验收判据，见 **D6**）。

## 背景（Context）

至今没有任何性能数字。SRS §3.6.2 写着一批指标（两机单向时延、串口有效吞吐达理论值 80%、框架附加时延 ≤5 ms、CPU 与 RSS 预算），但**没有测量手段**，这些指标一直悬着。

Fast DDS 3.6.1 自带两套成熟的性能测试，方法学可直接借鉴：

| | LatencyTest | ThroughputTest |
|---|---|---|
| 做法 | 发一条 → 等回显 → 计时，循环 N 次 | 按 burst 发 `n` 条 → 歇 recovery 毫秒 → 循环，跑满测试时长 |
| 报什么 | **RTT/2 − 实测时钟开销**；stdev / mean / min / 50% / 90% / 99% / 99.99% / max（µs） | 两侧分列：发送条数、耗时、packs/sec、Mbits/sec；接收侧另报**丢失条数** |
| 形态 | 同一可执行的两个角色，**双进程**，python 拉起 | 同上 |

其时钟开销是先跑 1001 次时钟读取标定出来再从每条 RTT 里扣掉的。

### 部署形态已定：两台 Linux 机器

**一台跑客户端 / publisher，另一台跑服务端 / subscriber**（2026-09-10 裁决）。这个前提解决了同进程形态下的两个硬问题：

| 问题 | 同进程形态 | 双机形态 |
|---|---|---|
| DDS 交付真实性 | 默认 `INTRAPROCESS_FULL`，同进程订阅方的回调**跑在发布线程上**（ADR-0013 实测），测的是同步函数调用而非通信 | **不存在**——走真实网络栈 |
| 串口吞吐的物理意义 | `openpty` **不遵守波特率**，测的是框架+PTY 开销 | **真实线缆**，波特率生效，SRS §3.6.2 的 80% 判据可验 |

代价是**单向时延测不了**（两机无时钟同步），只能照 Fast DDS 走 RTT/2。

> **⚠ 串口本轮不测（2026-09-10 裁决）**，见 **D5**。上表第二行因此**本轮不兑现**——双机形态在本轮的实际收益只剩第一行（DDS 交付真实性）与"贴近真实部署"。该行留在此处，是因为它仍是**串口将来接入时选择双机而非 PTY 的依据**。

## 决策（Decision）

- **D1（双进程双机，同一可执行两个角色）：** 一个可执行 `transport_perf`，经命令行选角色与介质：

  ```
  transport_perf --role client|server --medium tcp|udp|dds --suite latency|throughput [...]
  ```

  两端各自按同一份矩阵跑，**发起端打印最终表格**。

- **D2（时延口径照 Fast DDS，逐列对齐）：** `延迟 = RTT / 2 − 时钟开销`，时钟开销由 1001 次时钟读取标定。报表列与 Fast DDS **逐一同名**（`Bytes, Samples, stdev, mean, min, 50%, 90%, 99%, 99.99%, max`，单位 µs），便于横向比对。

  **RTT/2 隐含"来回对称"假设**，明确接受（见代价 1）。

- **D3（吞吐口径照 Fast DDS，但丢失必须由测试自行计量）：** burst 大小 × recovery 时间 × 测试时长；两侧分列统计。

  **框架不提供任何计数（ADR-0014），且写侧无背压、队列满时静默丢最旧并返回成功（ADR-0007 D3）**——故：
  - 发送侧只能报**入队条数**，不等于上线条数；
  - 接收侧的**实收与丢失，由测试在 payload 内嵌的自增序号算出**；
  - 报表须**同时**给出两侧数字，只看发送侧会得到好看得离谱的结论。

- **D4（控制与结果回传走被测传输本身，且复用框架自带的重发）：** 不另开控制通道。握手、开始/结束、结果回传一律 in-band，用**保留的 `message_id`（`ProtocolNode`）/ 保留服务名（`DdsNode`）**与数据流区分。

  **理由是"不为控制另设一套形态"**：另开一条 TCP 控制通道本身可行（本轮只剩 TCP/UDP/DDS 三种介质，都在网络上），但那会让被测形态与部署形态多一处分叉，且 Fast DDS 自身也是 in-band（控制走 DDS 命令 topic）。
  > 串口将来接入时，这条决策会从"可选"变成"必须"——两机之间只有那一条线。

  **控制消息一律走带重发的交互**（`RequestForResponse` / `RequestForResultDirect`），而不是 `Send`——UDP 会丢包，控制流不能丢。这等于用框架自己的重发能力兜住控制可靠性，不手搓一套。

  控制往返**必须落在测量窗口之外**，不计入任何统计。

- **D5（覆盖矩阵）：**

  | 被测面 | 介质 | 时延 | 吞吐 |
  |---|---|---|---|
  | `ProtocolNode::Send`（noresponse） | TCP / UDP | 需回显对端，RTT/2 | ✔ |
  | `ProtocolNode::RequestForResponse` | TCP / UDP | 天然 RTT | ✔ |
  | `ProtocolNode::RequestForResult` | TCP / UDP | **两个量**：到受理、到结果 | ✔ |
  | `ProtocolNode::RequestForResultDirect` | TCP / UDP | 单阶段 RTT | ✔ |
  | `DdsNode` 请求-响应 | DDS | 单阶段 RTT | ✔ |
  | `DdsNode` 发布-订阅 | DDS | 需回显对端，RTT/2 | ✔ |

  **串口本轮不测**（2026-09-10 裁决）。`--medium serial` **不实现**，传入即报错退出——不留一个跑不通的分支冒充已支持。介质维度做成可扩展的形状，将来接入串口只需补一个传输装配分支与其寻址参数，方法学与报表不变。

  **对端是另一个真节点**（`ProtocolNode` / `DdsNode`），订阅后按各模式的协议语义应答：`Send`→回一帧 `Send`；`RequestForResponse`→回 `kResponse`（同 `session_id`/`message_id`）；`RequestForResult`→先 `kResponse` 后 `kResult`（**框架自动补发的末尾那帧不由对端管**）；`RequestForResultDirect`→只回 `kResult`。

  > **更正（2026-09-11）**：本 ADR 初稿此处曾写"`ProtocolNode` 的服务端必须绕到节点下面（`ICodec::Encode` + `ITransport::AsyncWrite`），因为 `Send` 会覆盖 `session_id`"。**该限制已随 ADR-0019 消除**——`Send` 不再盖 `session_id`，服务端**只用公开面**（`Subscribe` + 填字段 + `Send`）即可回出合法应答帧。性能测试的服务端因此与客户端对称，都是真节点。
  >
  > 事实上，正是本 ADR 的服务端设计暴露了那个接口缺口，才有了 ADR-0019。

- **D6（只报数，不做 pass/fail）：** 与 Fast DDS 一致——性能数字进断言必然抖。`transport_perf` 输出表格即完成使命。

  **由此它是 SRS §3.6.2 的证据来源，而不是验收判据本身**：判据成立与否由人读数后裁定。

- **D7（独立可执行，不进 `transport_tests`）：** 性能测试慢且抖，混进单元测试会污染"236/253 全绿"这个口径，也会拖慢每次构建。`transport_perf` 单独一个目标，**须同时登记 CMake 与 qmake 两套清单**（仓库既有的双清单义务）。

- **D8（payload 矩阵封顶 63 KB）：** `SystemCodec` 的 `frm_len` 是 `uint16`，body 上限 65535，故 Fast DDS 矩阵里那行 1 MB 做不了。取 **16 / 256 / 1024 / 16384 / 63488** 五档，三个介质**统一**（DDS 本可更大，但统一封顶才能横向比）。

  > UDP 另有其自身的报文上限（约 63 KB 可用净荷），与本档位上限接近，故同一张矩阵对 TCP/UDP/DDS 均可用。

- **D9（预热与握手排除在测量之外）：** 每一行矩阵开测前先跑一轮预热（默认 100 条，不计入），把链路建立、DDS 发现窗口（约 240 ms）、首帧路径上的惰性开销全部付掉。

- **D10（不为测量给库加计数或钩子）：** 不为测量加任何计数器、trace 钩子或观测接口。所需的一切（序号、时间戳）都放在 payload 里由测试自理。

  > **更正（2026-09-11）**：初稿写的是"本轮只加测试代码，不动库"。**该约束已被 ADR-0019 突破**——`Send` 的盖章语义确实改了库。但改动的动因是**接口缺口本身**（服务端写不出应答），不是"为了测量而加钩子"。**D10 的实质约束仍然成立**：不为测量目的给库加任何东西。

## 明确接受的代价

1. **RTT/2 隐含"来回对称"假设。** 去程与回程若不对称（如非对称链路、一侧 CPU 更忙），该数字会系统性偏离真实单向时延。**双机无时钟同步，这是唯一可行口径**，Fast DDS 亦然。

2. **发送侧数字不代表上线量。** 写侧 fire-and-forget、队列满静默丢最旧且返回成功——**过载时"发送 packs/sec"会虚高**。报表必须两侧并列，且解读时以接收侧为准。这是 ADR-0007 D3 的直接后果，不是测量缺陷。

3. **控制流量与被测流量共用同一条链路。** 控制往返虽在测量窗口之外，但它占用同一条连接/topic。影响限于窗口切换的间隙，不污染窗口内的采样。（串口将来接入后，它还会占用同一波特率预算，届时这条代价更实在。）

4. **不做 pass/fail，故不能自动守护性能回归。** 某次改动让时延翻倍，CI 不会红——只有人主动跑并比对历史数字才发现。**这是明确接受的**：把抖动的数字接进 CI 的代价（长期误报、进而被忽略）比它挡住的问题更大。

5. **`RequestForResult` 的两个量之间存在对端实现依赖。** "到受理"与"到结果"的间隔取决于**对端何时产出结果**，而对端是我们自己的测试节点，它是立即回结果的。故该间隔测的是框架开销的下界，**不代表真实业务**。

## 影响（Consequences）

- **正面：** ① SRS §3.6.2 的指标首次有测量手段；② 四种交互模式 × 三种介质的开销有了横向可比的数字；③ 与 Fast DDS 同名同列，可直接对比"用了本框架比裸 DDS 多花多少"。
- **本轮未兑现：** SRS §3.6.2 里**串口有效吞吐达理论值 80%** 那条**仍无证据**——串口本轮不测（**D5**）。该条继续悬着，与 #199（PTY 验不了 `data_bits`/`stop_bits`/`parity`）同属"串口需实机"这一类。
- **负面（明确接受）：** 见上五条。
- **对 SRS：** §3.6.2 补一句说明"证据由 `transport_perf` 产出"；`RT_TESTABILITY` 补该工具的存在与定位。
- **对 SDD：** 新增一节描述 `transport_perf` 的形态与两侧统计口径。
- **对 README：** 「构建」一节补 `transport_perf` 的构建与双机跑法。

## 备选方案（Alternatives considered）

- **同进程两节点对接 loopback。** 工作量小得多，且**同一时钟可测真正的单向时延**（Fast DDS 做不到）。**否决理由：** 部署形态已定为双机（2026-09-10 裁决）；且同进程下 DDS 走 `INTRAPROCESS_FULL`、串口走 PTY，两者测出的都不是通信本身。
- **另开一条 TCP 控制通道。** 控制与被测流量彻底隔离。**本轮三种介质都在网络上，这条本是可行的。否决理由：** 它会让被测形态与部署形态多一处分叉，而 Fast DDS 自身也是 in-band（控制走 DDS 命令 topic）；且串口将来接入后这条路会走不通（两机之间只有那一条线），届时还得改回 in-band。
- **控制消息用 `Send` + 自建重发。** **否决理由：** 框架已有带重发的交互，手搓一套等于重复实现且更容易错。
- **把性能测试接进 `transport_tests` 并设阈值断言。** **否决理由：** 见 **D6/D7**——数字抖动会让 CI 长期误报，最终被无视；且会拖慢每次构建。
- **照 Fast DDS 提供 python launcher。** **否决理由：** 双机部署下 launcher 要处理跨机 ssh 与结果汇集，收益不抵复杂度。本轮两端各自手工拉起。
