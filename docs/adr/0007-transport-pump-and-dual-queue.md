# ADR-0007：传输层统一为「socket 管理泵 + 读写双队列」，读接口返回等待器

> **注（2026-08-19）**：本 ADR 的泵形态（**D1**）与 fire-and-forget 写（**D3**）被 ADR-0008 保留并扩展，但**接口表达已改写**：`Read()`→`AsyncRead()`、`Write(SendUnit)`→`AsyncWrite(Datagram)`（**D4 的「写侧也交队列句柄」未采纳**）、`RequestClose()`→`Close()`、`WaitClosed()` 去掉时限参数。**D5（静默超时）已落地**，且与 bind 失败的重试间隔合并为同一个 `UdpConfig::silence_timeout`（默认 5s），故 D2 中「固定 3 秒」改为该配置项。

**状态：** Accepted
**日期：** 2026-08-12
**关联：** ADR-0004（传输语义统一——本 ADR 改其 **D1** 的终止表达、扩大其 **D6** 连接泵形态至全介质）；ADR-0005 **D5**（致命错误自终——本 ADR 缩小其适用介质）；#152（AsyncTask 升级后 channel 默认有界 1024 且静默丢最旧）；SRS 落点：RT_TRANSPORT_004/008、RT_TCP_RECONNECT_003、RT_LIFECYCLE_008、新增心跳配置。
**实施范围：** 本轮**以 `UdpTransport` 为样板先行**；TCP/串口按同一形态后续跟进（策略差异见 D6）。

## 背景（Context）

三个介质的传输实现形态各异：`TcpClientTransport` 在 #109 已改为「连接泵 + 对外通道」（ADR-0004 D6），而 `UdpTransport`/`SerialTransport` 的 `Read()` 仍**直接 await socket 读流**并以 `active_read` 守卫单读。node 侧因此仍要为不同介质承担不同的失效假设。

同时暴露出三处结构性问题：

1. **socket 生命周期与数据面缠在一起** —— 重建 socket 会波及正在等待的读者。
2. **读只能有一个消费者**（`active_read` 守卫）——而"同一份入站数据分发给多个消费者"是真实需求，只能在更上层重复造扇出。
3. **写侧无排队** —— 并发写靠加锁串行化，链路不可用时直接拒绝，没有"待发"这一状态。

## 决策（Decision）

- **D1（统一形态：外层 socket 管理循环 + 内层数据泵 + 读写双队列）：** 每个传输内部持两条 `Coro::Awaitable` 队列：**`read_queue`**（传输作生产者，把 I/O 收到的数据投入）与 **`write_queue`**（传输作消费者，取出待写 I/O 的数据）。`Start()` 起泵：

  ```
  外层循环（socket 管理）:
    while (未被 Close) {
      按配置创建并就绪 socket;        // UDP: bind;TCP: connect
      失败 → 等固定间隔后重试;
      stream = coro(socket).readAll()/receiveDatagram();
      内层循环（数据泵）:
        while (1) {
          r = await stream (带静默超时);
          if (r)        → push 进 read_queue;
          else          → break;       // socket 关闭 / 静默超时 → 回外层重建
        }
    }
  ```

  `Read()` 退化为"交出 `read_queue` 句柄"，`Write()` 退化为"投入 `write_queue`"。socket 的重建对两端完全透明。

- **D2（UDP 改为无限重试，仅 `Close` 终止）：** UDP 的 socket 创建/bind 失败或读流终止时，**等固定 3 秒后重试，永不自终**；唯一的退出条件是我方 `Close`。
  **推翻** ADR-0005 D5 与 RT_LIFECYCLE_008 中"UDP 属非重连节点、致命错误应自终"的结论。**自终的适用介质缩为：串口、TCP 服务端已接受的连接、DDS。**
  依据：UDP 无连接，bind 失败多为**暂态**（接口未就绪、地址尚未配好、端口短暂被占），把它等同于"连接的生命等同节点生命"并不成立；把节点因暂态 bind 失败而终结，宿主除了重建整个节点别无选择。

- **D3（写侧 fire-and-forget，`write_queue` 等待链路可用）：** `Write()` 把整包投入 `write_queue` 即返回，**不等待实际发出**；发送失败不作为 `Write()` 的返回值，只进 `LastError()` 与 Trace。链路不可用时数据**留在队列中等待链路恢复**，不拒绝、不丢弃。
  **推翻** RT_TCP_RECONNECT_003（"`Connecting`/`Reconnecting` 下新发送立即返 `Connection`，不得缓存等待重连"）。
  **已定案（2026-08-12）：接受一次性灌出。** 链路恢复后积压报文按序全部发出，不做帧级时效、不在重连时清空队列。对端因此可能收到一批已过期的数据——**这是明确接受的代价**，非疏漏。
  否决的备选：帧级时效（需要每帧带时间戳并在发出前判活，把"数据新鲜度"这一**应用语义**塞进纯字节管道，违反三层解耦）；重连时清空（会丢掉本可送达的数据，且同样无归因）。
  **与 D6 的相互作用**：在队列容量策略定案前，channel 默认「有界 1024 + 丢最旧」意味着长时间断链后实际灌出的是**最新的 1024 包**、更旧的已被静默丢弃。这一"隐式的新鲜度过滤"是当前默认行为的副产物，**不是设计意图**，也未归因；D6/TBD-009 定案时须一并处置。

- **D4（`Read()` 返回等待器，删除单读约束与 `OperationOptions`）：** `ITransport::Read()` 由 `Result<Datagram> Read(OperationOptions)` 改为**返回 `read_queue` 的等待器句柄**（`std::shared_ptr<Coro::Awaitable<Datagram>>`），不再接受 `OperationOptions`——deadline 与取消由调用方自行在句柄上 `await_for` / 接令牌。
  **是否共享由调用方决定**：需要多消费者扇出时调用方自行 `shared()`（AsyncTask `ffdda11` 起提供）；不共享则多个消费者天然抢占——**socket 的 read 本就是抢占式的**。
  **删除 RT_TRANSPORT_004 的"同一时刻至多一个有效读"约束**与实现中的 `active_read` 守卫。
  **改写 ADR-0004 D1 的终止表达**：终止不再表现为"`Read` 返 `kClosed`"，而是**队列被 `close()` 并携带终止原因**，调用方 `await` 得到该终止错误。"仅我方 `Close` 才终止"这一**语义不变**。

- **D5（静默超时可配、可关）：** 内层数据泵支持**静默超时**（指定时长内无数据即判链路故障、退出内层回外层重建），经配置项设置，**`0` 表示禁用**。
  理由：并非所有部署都有周期性流量，静默链路不得被误判为故障；故默认禁用，由宿主按其协议的心跳约定开启。

- **D6（队列容量与丢弃归因：暂缓，但记录约束）：** 本轮不定 `read_queue`/`write_queue` 的容量策略。**遗留约束**（见 #152）：
  - AsyncTask `ffdda11` 起 channel **默认有界 1024 且静默丢弃队首最旧值**。对 UDP，队列元素是**完整应用包**，1024 包被判定为暂时够用。
  - **该推理不适用于字节流介质**：`readAll()` 吐的是任意字节切片而非完整包，丢中段即帧错乱。TCP/串口跟进本形态时**必须**另定策略（ADR-0004 D6 的结论是"有界且满时阻塞生产者"）。
  - **任何丢弃都必须归因**（新增 `DropReason` + `RecordDrop`），否则 §3.6 的 `Σ命名原因 == 总丢弃` 与 `drop_records.size() == Σ` 破裂。当前默认行为是**静默**丢弃，属活跃隐患。

## 影响（Consequences）

- **正面：** 三介质形态统一，node 侧不再按介质承担不同失效假设；socket 重建与数据面解耦；多消费者扇出由调用方按需 `shared()`，无需在传输层设单读守卫，也无需在上层重复造扇出；写侧有了"待发"状态。
- **负面（明确接受）：** ① UDP 不再自终，故障 UDP 节点将无限重试而非收敛——宿主失去"节点自己死掉"这一信号，只能经链路可用性/观测面判断；② 写入不再同步返回失败，调用方失去即时错误反馈，只能经 `LastError()`/Trace 事后得知；③ `ITransport::Read()` 签名变更波及全部传输实现、node 读循环与大量测试（破坏性）；④ 链路恢复后积压报文一次性灌出，对端可能收到过期数据（D3，已定案接受）；⑤ 队列容量与丢弃归因未定，默认静默丢弃隐患存续（D6/TBD-009）。
- **对 ADR-0004：** **D1** 的终止表达改写（语义不变）；**D6** 的连接泵形态由 TCP 客户端扩大至全介质，其"对外通道无界"的登记被 #152 取代。
- **对 ADR-0005：** **D5** 自终的适用介质缩小，不再含 UDP；其余不变。

## 备选方案（Alternatives considered）

- **保持 `Read()` 返回 `Result<Datagram>`、在传输内做扇出**：否决——扇出策略（谁该收到、是否复制）是调用方的语义，传输层无从判断；且必然重新引入单读守卫这类约束。
- **UDP 保持自终**：否决——bind 失败多为暂态，因暂态故障终结节点会迫使宿主重建整个节点（D2）。
- **写侧保持同步返错**：否决——与 `write_queue` 排队形态不相容；同步返错要求 `Write` 等到实际发出，那 `write_queue` 就退化成一把锁（D3）。
- **链路不可用时丢弃 `write_queue` 内容**：否决——会丢掉本可送达的数据，且同样无归因（D3）。
- **帧级时效（每帧带时间戳、发出前判活）**：否决——"数据新鲜度"是应用语义，塞进纯字节管道违反三层解耦；真需要时应由编解码层或应用自行携带并判定（D3）。
