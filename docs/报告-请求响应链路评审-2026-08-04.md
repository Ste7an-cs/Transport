# ProtocolNode 请求-响应实现评审报告

**日期**:2026-08-04(评审)/ 2026-08-05(整改落地台账更新)
**评审范围**:请求-响应核心链路 —— `ProtocolNode` / `PendingTable` / `NodeRuntime` / `SharedCompletion` / `BoundedQueue` / `Observability`,兼看 `DdsNode` 对称部分。
**整改状态**:全部结论已通过 issue #98 / PR #99「P6 前置清理」落地(master `7994719`);本文档保留评审原貌并逐项标注当前状态,兼作整改台账。

---

## 0. 总体结论

链路本身健康:请求-响应核心路径清晰、三层解耦与"无共享引擎"纪律执行到位,多数"看起来复杂"处都有 ADR 依据且有注释锚定。真正的冗余很少且都是小件;主要维护性风险不在架构,而在三处工程细节 —— **锁内调用用户 sink(潜在死锁)、trace 类别魔法字符串散落(含一处命名误导)、session_id 手工归还纪律**。

- **冗余设计**:有,但都是小件(死成员、重复 include、双重限流、Close 两分支重复),无架构级冗余。
- **是否过度复杂**:核心仲裁的复杂度与其所解决的竞态相称,不算过度;两个 node 的平行是"不共享引擎"红线的自觉代价,当前在可控边界内。
- **是否难维护**:目前不难,但 M1–M4 四处是明确的"未来 bug 形状",工作量都小 —— 已在 P6 开工前一并清掉。

## 1. 请求-响应实现详解(评审时现状)

一次 `Request` 的完整生命线,涉及四个组件,职责切分如下:

```
调用方 fiber                          读循环 fiber
────────────                          ────────────
ProtocolNode::Request                 NodeRuntime::SpawnReadLoop 骨架
  1. IsRunning 门禁                     transport_->Read() ─┐
  2. AllocateSession (LRU 空闲集)                            │ Datagram
  3. 盖章 frm_type/protocol_id/session   ProtocolNode::DecodeAndDispatch
  4. request_key(req) → 派生键            codec_->Decode → Message[]
  5. PendingTable.Register(key)           ProtocolNode::Dispatch
  6. codec_->Encode → Write                 kResponse/kResult?
  7. handle.Wait(deadline/token) ◄────────── response_key(msg) → Resolve(key, msg)
  8. (lease 析构) ReleaseSession            (未命中 → kUnmatchedOrLateResponse 归因)
```

- **出站侧**:`Request` 查 `IsRunning`,从 256 个 session_id 的空闲 deque `pop_front` 取最久释放者(FIFO 复用最大化"退休窗口",降低迟到响应误配概率);盖章后用注入的 `request_key` 派生 `uint32` 键,`PendingTable.Register` 唯一登记,Encode + Write 上线,`handle.Wait` 挂起。
- **入站侧**:读循环骨架在 `NodeRuntime` 里只做 `Read → 错误分类 → 回调`,不碰协议;`DecodeAndDispatch` 解码,`Dispatch` 内联终结判别(`kResponse`/`kResult`)—— 响应帧走 `response_key` 归一化(清 `0x1000` 标记位)后 `Resolve`,业务帧入有界队列或归因丢弃。
- **仲裁核心**(`PendingTable` + `SharedCompletion`):每个在途 entry 是一个 `SharedCompletion<Message>` 信箱,**Resolve / 超时 / 取消 / FailAll 四方抢同一个原子首胜 `Complete`**,天然恰好一次终结。`Handle::Wait` 里有关键的二段仲裁:本地超时/取消后不直接返回,而是先尝试 `Complete(error)` 把 entry 置终结 —— 若抢输了(Resolve 恰在同一瞬间胜出),改用真正的终结结果。这堵住了"本地超时返回但 entry 未终结、随后 Resolve 假成功"的竞态缝。Handle 析构兜底 `Evict`(按 entry 身份匹配摘除,不误删同键新登记)。
- **收敛路径**:Close 时 `FailAll(kClosed, latch)` 令在途全部恰好一次收敛并堵新登记;断连时 reactor fiber `FailAll(kConnection, 不 latch)` 只清当前代际、表继续可用 —— 连接概念靠"清空 ⇒ 在途恒属当前代际"这一不变式隔离,没有下沉进 PendingTable。

**设计优点(实在的)**:恰好一次终结不靠状态机枚举而靠原子首胜,竞态面小;PendingTable/BoundedQueue/NodeRuntime 三个基座协议无关,DdsNode 换个 Key 类型就复用(D10 已实证);终结判别、键派生等协议语义全内联在 node,没有"上帝引擎"。

## 4. 维护性风险(按优先级)

| 编号 | 风险 | 状态 |
|---|---|---|
| **M1**(最高) | **持锁调用用户代码 `sink->OnTrace`,有重入死锁埋雷**。三处一致:`ProtocolNode::Dispatch` 在 `mutex_` 内、`BoundedQueue::Push` 在队列锁内、`NodeRuntime` finalizer 在 `mutex_` 内逐条 close_drop。`RecordDrop` 会调用用户实现的 `OnTrace` —— 用户 sink 若在其中回调任何 node getter,即同一把 `std::mutex` 递归加锁,死锁/UB。旧契约只写"须线程安全",未写"禁止重入 node API"。 | ✅ 契约硬化(#99):`ITraceSink` 写明 OnTrace 可能在库内锁临界区被调,必须快速返回、不得阻塞、不得回调本库任何 API;`RecordDrop` 文档同步警示。（取"补契约"而非"挪锁外":锁外方案需拆 RecordDrop 计数/trace 两段,引入新的锁外时序面,权衡后择低风险项。） |
| **M2** | **trace 类别是散落魔法字面量,且有一处命名误导**。九类字符串分散 5 个文件、无中央常量,loss=0 harness 靠 `category=="drop"` 过滤 —— 打错一个字母即静默产生新类别、测试筛不到,编译器无从发现。更扎眼:`NodeRuntime::MarkRunning` 里 `RecordEvent("close", ..., "running")` —— **Created→Running 跃迁挂在 "close" 类别下**,读 trace 者会直接误判。 | ✅ 集中 + 改名(#99):新建 `core/TraceCategories.hpp` 单一权威,12 个发射点全改常量;生命周期类别 `"close"` → `"lifecycle"`;同步 SDD §6 / ADR-0003 D13 九类清单与 `trace_wiring_test`。 |
| **M3** | **`Request` 的 session 归还是手工纪律,共 4 处**。注释自陈"任一提前返回都须归还,否则在途预算泄漏,终致假 kResourceExhausted"。靠注释守的不变式即未来 bug 形状:后人在 Register 与 Wait 之间插新提前返回(如 P6 限流)漏归还,泄漏是慢性的、压测难第一时间归因。 | ✅ RAII 化(#99):`SessionLease` 析构自动归还,4 处手工 `ReleaseSession` → 0 处。 |
| **M4** | **`Send` 借道 session 空闲集,有两个非显然副作用**。副作用一:256 全在途时 Send 也被拒(它不需唯一性预算)—— 有意的边界策略但 SRS/SDD 无落点。副作用二更隐蔽:每次 Send `pop_front` 消耗"休息最久"的 id 又 `push_back` 成"最新鲜",**高频 Send 持续搅动 FIFO,削弱 Request 迟到响应退休窗口**(RT_REQUEST_005 立身之本)。 | ✅ 改只读尾部盖帧(#99):`Send` 只读空闲集尾部(最新释放者)盖帧、不出队 —— 不扰动 FIFO、不占预算;256 全在途仍拒绝(既定边界策略不变)。**实现偏离评审初拟的"独立计数器"**:独立计数器可能盖到正在途的 id、削弱误配防护;只读尾部零新状态且保留全部性质。补回归测试 `NoresponseSendDoesNotDisturbSessionFifoOrBudget`。 |
| **M5**(低) | **`has_handler_` 无锁读写**。`SpawnHandlerLoop` 裸写 `= true`,`Close` 锁外裸读。当前安全依赖"bring_up 从 MarkRunning 到 SpawnHandlerLoop 无挂起点、单调度线程"的时序巧合;但 MarkRunning 先置 Running,跨线程 Close 理论上可在 handler spawn 前进来读到 false,finalizer 就不等 handler 退出了。全类都用 mutex 表明预期多线程,此字段不该例外。 | ✅ 挪进锁内(#99) |

## 5. 复杂但有依据(不建议动)

初读最"吓人"、但复杂度是真实问题换来的,动它们只会把复杂度换个地方藏:

- **`Handle::Wait` 的二段仲裁**:看似绕,实为修 `SharedCompletion::Wait` 本地超时不置终结的缺口 —— 不这么做就有"超时返回后 Resolve 假成功"窗口。注释已把动机写清。可议点:这层补丁长期看是否该下沉进 SharedCompletion 本身;但那会改变 `start_done_`/`closed_` 等其他用户语义,P6 前不值得动。
- **`Resolve` 的两段加锁**(find→解锁→Complete→重锁→按身份 erase):锁外 Complete 是为不在表临界区里唤醒等待者(D8 纪律),身份比对防误删同键新登记。教科书式正确写法。
- **PendingTable 染上 latency/trace**(P5-4):"薄基座"确实比 P1 厚了 —— 但请求时延的唯一准确定义点就是 Register→终结,放别处都要多一次跨组件握手。接受这点厚度,但应警惕它是斜坡:**P6 加直方图时不要继续往 PendingTable 里塞**,届时把"终结回调"开成注入点让 node 自己聚合更干净。
- **`Close` 的重入自锁防护 + 独立 finalizer fiber**:handler 里调 `RequestClose` 等自己退出 = 死锁,这套防护是 RT_LIFECYCLE_005 的直接实现,测试有覆盖。

- **有无冗余设计?** 有,但都是小件(死成员、重复 include、双重限流、Close 两分支重复),无架构级冗余 —— 已清。

- **是否难以维护?** 评审时不难,但 M1–M4 四处是明确的"未来 bug 形状",均小工作量 —— 已在 P6 开工前一并清掉;剩 C2/C3 两项按依赖条件延后,不构成当前维护负担。
